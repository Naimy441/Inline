A product & architecture proposal

Canvases

Beautiful documents created with Claude, directly editable in both Flow and Pages, with PDF layout visible throughout the work.

“Change the design as much as you like.
My edits remain mine.”
October 17, 2026 · Grounded in Inline’s existing architecture · Concept, not an implemented feature
Architecture decision / updated

Two editable views. One document. Which foundation?

Recommendation: editor authority, HTML design, explicit pagination contracts

Choose Path A for Inline: extend the existing editor with a canvas-specific semantic schema and expressive HTML/CSS components. Keep browser-native rendering, but constrain the layout vocabulary to patterns whose editing, fragmentation, capture, and export are defined. Reuse editing and revision infrastructure; budget substantial work for rich layout and browser-based capture. This is a researched architectural recommendation, not a benchmark or implemented prototype.

What already exists in Inline

pagination.ts measures line boxes in one continuous ProseMirror document and inserts spacer decorations. PageCanvas.tsx draws sheets behind it and keeps the same editor tree in Flow and Pages. documentSession.ts exposes setFlow, while hub.ts supplies versioned mutations. This avoids splitting paragraphs into separate editable copies merely because they cross a page. The current Flow mode primarily serves phones; desktop switching still needs product work.

Path A: how it would work

Add semantic canvas sections, visual themes, figures, comparison grids, and typed design properties. Use trusted node views and editable descendants. Extend pagination through component contracts: flowing text may split by line; tables by supported row boundaries; short comparisons remain atomic; oversized components must provide an explicit continuation or reflow behavior. Backgrounds, borders, and repeated elements need page-fragment-aware decoration rather than a single naive box spanning the page gap.

Path A: why it fits the requirements

Normal text editing, undo, selection, user/Claude synchronization, and revision history remain in the existing editing model. Both views can be genuine editing surfaces because they are alternate layouts of the same active editor. Page pictures and layout diagnostics can retain familiar agent tools. HTML remains the visible rendering medium; a semantic source does not imply visually plain documents.

Path A: the real limits

The current pagination code collects known text blocks, a small set of recursive containers, table rows, and indivisible boxes. It is not a general CSS fragmentation engine. Two independently flowing columns, cross-page grid cards, full-height decorative surfaces, variable page masters, and arbitrary positioned content need new algorithms or deliberate constraints. Do not promise arbitrary generated HTML or arbitrary JavaScript as fully editable. Adding a node view alone does not solve any of these pagination problems.

Path B: how it would work

Store semantic content or source HTML/CSS, render it with a publishing engine such as Paged.js or Vivliostyle, and expose the resulting pages. These engines supply an existing paged-media pipeline. To make output pages editable, add source-to-fragment text mapping, model transactions, selection mapping, undo integration, IME-safe editing, and rerender scheduling. Reuse the document hub and agent tools where possible; the editing integration is the new core work.

Path B: the benefit

A publishing engine is attractive when page masters, running content, footnotes, and complex print-oriented CSS dominate the requirements. It can reduce the amount of publishing behavior we implement ourselves. Engine support varies by feature and layout; representative designs must be tested rather than treating HTML support as universal.

Path B: the hidden cost

Paged.js documents a chunker that fragments source content into generated page DOM. Vivliostyle documents its viewer as a typesetting/display application. These are useful publishing foundations, but the reviewed interfaces do not establish a complete rich-text editing contract. My engineering inference: making generated page fragments behave like one editor requires a substantial integration layer. contenteditable on each page cannot by itself preserve cross-page editing, source identity, or caret stability during repagination.

Do not choose a misleading hybrid

A normal editor beside a read-only paginated preview fails the requirement that Pages be editable. Another risky shortcut is editing isolated text overlays: that can support copy corrections but usually does not provide continuous selection, structural editing, or natural paragraph flow across pages. A publishing renderer used solely for export also risks a different composition from the editable view.

The screenshot and export correction

Current picturePage calls pdfModel and rasterizes that model; it is not a generic browser screenshot of all CSS effects. The PDF model represents text, rectangles, lines, images, and links. Reusing it unchanged would create a styling ceiling. For canvas tools, capture the settled paginated DOM in a browser, at a pinned revision and layout profile. Print/export that same paginated DOM. Reuse the tool names and workflow, but replace the canvas-specific rendering backend.

Page references must be revisioned

Claude can inspect page 3 of revision 42, but a later edit may move that content. Return block IDs, source ranges, layout revision, paper geometry, and page number with every capture. Resolve changes against content identities and reject or refresh stale page references. A shared document revision does not guarantee identical page breaks across two browser engines or font environments; use a controlled layout profile for agent inspection and export.

One active editor first; split view is additional scope

Start with a Flow / Pages switch that preserves selection using model positions or bookmarks. Both modes support the full relevant edit commands. Expose paper-only design controls in Pages and preserve those settings in Flow. If both are visible together, prefer an active editing pane and synchronized companion initially; two simultaneously editable panes require careful shared transaction and selection management. This is separate from making both switchable modes editable.

A fair comparison prototype

Use the same content, styles, fonts, assets, and editing tasks in both candidates. Include long prose, two-column layouts, a multi-page table, a captioned figure, a section background crossing a break, non-Latin text, and an oversized component. For Path B, actually edit the paginated output—source editing with preview is not a passing substitute. Record caret jumps, content loss, undo correctness, input delay, repagination time, and export differences. No such comparative runtime results have been measured yet.

When I would reverse the recommendation

If broadly arbitrary HTML/CSS publishing is a launch requirement, or continuous multi-column content and sophisticated page masters matter more than rich editing continuity, Path B deserves priority. If the Path A prototype cannot support the actual intended designs without adding one-off pagination rules for each, revisit its layout core. Do not keep expanding the existing spacer algorithm indefinitely merely to preserve prior investment.

Build decision

For the requirements as stated—Claude-designed artifacts, genuine manual editing in either view, page inspection, and visible PDF composition—Path A has the better starting fit. Add a real design layer and real browser capture rather than simply expanding the current document toolbar. Keep a renderer interface and benchmark fixtures so a publishing engine can be evaluated later without replacing document storage, history, or the Claude integration.

01 / Vision

Documents that feel designed, stay editable, and travel well.

The promise

Ask Claude for a useful artifact. Receive a designed document with two fully editable presentations: Flow for uninterrupted composition and Pages for working directly on the intended PDF layout. Change text or structure in either view, switch without losing your place, and keep one coherent history.

A deliberate shape

Flow and Pages are equal editing modes over one semantic document. Pages includes actual paper geometry, margins, running elements, and live reflow. Flow removes paper boundaries and can adapt to screen width. Page-level rules persist in the model and appear as unobtrusive markers or settings in Flow. Automatic page numbers describe layout, not permanent content ownership.

The experience to aim for

A user uploads messy project notes and asks for a client proposal. Claude creates an editorial introduction, scope, milestones, and pricing. The user corrects the scope inline, selects the pricing section and asks for a comparison, then requests a restrained blue brand treatment. Their correction survives. Printing produces an orderly proposal with readable tables.

What makes this valuable

The distinguishing workflow is designing and editing the final pages together with Claude. Users can work in Flow or directly on paper, Claude can inspect and refine individual rendered pages, and export captures a composition both have already seen. Preserving user edits through redesign remains a core promise.

02 / Use cases

Prioritize work people revise and eventually give to someone else.

Client proposals and project briefs

Notes become scope, options, deliverables, timeline, and pricing. Users edit commitments directly. Claude can change visual hierarchy or rearrange options. The PDF becomes the client handoff. This is a strong first launch workflow.

Research and decision briefs

Turn source documents into an executive summary, evidence, comparisons, and a recommendation. Keep source references attached to claims and expose uncertainties. A visually persuasive canvas must not conceal weak evidence. Export references as readable endnotes.

Study guides and teaching materials

Combine explanatory prose, worked examples, vocabulary, diagrams, and exercises. Users correct terminology and add their own notes. Online answers can expand; print can place them in an answer section. Every hidden section has an explicit export policy.

Plans, reports, and reference sheets

Launch plans, event schedules, onboarding guides, nonprofit reports, recipes, travel itineraries, resumes, and portfolios benefit from flexible hierarchy and repeatable design. Dense numeric reports need editable underlying data and semantic tables, not pictures of numbers.

Where to draw the boundary

Prefer the existing paginated document editor for exact page composition and established Word workflows. Prefer a spreadsheet for substantial calculations and a dedicated app for live operational workflows. Canvases can link to these artifacts and present a stable, readable summary.

03 / Editing

Editing should feel like touching the finished document.

Quiet by default, discoverable on demand

The reading surface has no permanent input borders. Clicking text places the caret; hovering or keyboard focus reveals a small block handle. Selection reveals formatting and Ask Claude. A first-use hint explains direct editing. Read-only mode and a keyboard-accessible outline make the mode clear.

Text and structure are different actions

Normal typing, selection across paragraphs, paste, IME composition, links, undo, and redo belong to the rich-text engine. Section moves, column changes, image crop, and chart data use intentional controls. A person should be able to make small changes without asking Claude or seeing source code.

Precise AI targeting

Ask Claude receives stable section and block IDs, selected text and its revision, the requested scope, relevant nearby content, and optional geometry or a screenshot. Distinguish rewrite text, restyle section, rearrange layout, and redesign the canvas. A visual change should preserve wording unless the request also asks for rewriting.

Keep user edits through an AI turn

Claude prepares a versioned patch against a known base. Text steps can rebase through compatible edits; structural operations need explicit preconditions. If a user changes the same material, offer the conflicting proposal for review. Never resolve an overlapping edit by silently taking the model's full replacement.

One coherent history

Typing has familiar fine-grained undo. A Claude operation has a named checkpoint such as Restyled proposal, with review and restore. Group content and design changes in one atomic revision. Locks can protect exact wording, figures, or a whole section; locks are enforced by the mutation service.

Accessibility is part of editing

Keep headings semantic and DOM order meaningful. Support keyboard-only section movement, accessible menus, clear focus rings while editing, contrast, reduced motion, alt text, and real table headers. Cross-column selection and nested-container keyboard behavior deserve an early editor spike.

04 / Design

Give Claude a visual language with room for expression.

Three layers of control

A canvas theme defines typography, colors, spacing, width, and density. Section recipes define editorial introductions, sidebars, comparisons, timelines, figures, and data layouts. Typed local overrides provide specific refinements. Content uses stable IDs and remains independent from these presentation decisions.

Taste comes from composition

Vary rhythm, information density, typography, image treatment, and whitespace. Use semantic visual hierarchy rather than wrapping every paragraph in a card. Provide several art directions—editorial, technical, warm, compact—with meaningful structural differences. Brand kits should include print colors and available fonts.

Customization in ordinary language

Requests such as make this feel like a field guide, use my brand, make the pricing easier to compare, or preserve all words but make it more compact map to explicit design operations. Show a reversible candidate for major redesigns. Let users save a finished design as a reusable template.

Avoid a fixed-template ceiling

Use composable primitives, not a tiny list of immutable templates: sections, stacks, constrained grids, text, figures, labels, rules, and surfaces can create many designs. Add new audited recipes as real use cases demand. Explain when an unusual request exceeds the supported layout vocabulary.

Advanced custom visuals

Later, allow isolated custom components with declared editable text/data slots, size constraints, and a required static print rendition. Unrestricted generated React cannot honestly guarantee direct editing and printable layout. Treat custom code as a separate capability with stricter isolation and a visibly defined contract.

05 / Architecture

Extend Inline's document authority; keep generated code out of the normal document path.

Versioned authorityValidate, merge, persist

Two presentationsEditable screen · printable document

The canonical model

Use a versioned artifact envelope: kind, schemaVersion, revision, theme, printSettings, assets, sources, and a semantic content tree. Add canvas section/container nodes to a canvas-specific ProseMirror schema that shares text primitives. Keep IDs stable; reference presentation settings by ID. One authoritative model must describe content, design, and their revision together.

Editing and rendering

Recommended: retain one ProseMirror content model and editing authority, enrich its HTML/CSS rendering with canvas-specific nodes, and add layout contracts for supported components. Switch one active editor between Flow and Pages while retaining selection. Do not mount two independent editable copies. Simultaneous side-by-side editing would need shared-state views and explicit focus/selection coordination as additional work.

Mutation authority

All manual and agent changes pass through a versioned transaction service. Use ProseMirror steps for prose and validated operations for design, moves, and typed data. Check base revision, target IDs, locks, ownership, and schema constraints; persist the accepted result atomically; broadcast one ordered revision. Design metadata must not bypass the text transaction's ordering.

Reuse what Inline has

The current documentSession already handles instant local edits and versioned ProseMirror collaboration. hub.ts is the document authority. schema.ts has stable block IDs. store.ts writes local files, and repo.ts supplies Git-backed history. Claude's MCP tool registry and render/measurement infrastructure offer natural integration points. These are building blocks, not evidence that a canvas implementation already exists.

Suggested module boundaries

Add lib/canvas/model for validation and migrations; renderer for shared screen/print interpretation; editor for container node views and selection; operations for atomic versioned mutations; print for print rules and preflight. Expose a canvas workspace and print route through the existing app. Keep paginated layout and its PDF writer as a separate rendering path.

Assets and portability

Store referenced images, fonts, and chart data with the artifact or in its managed asset store. Record ownership and versions. Export portable HTML as an additional handoff option later. Converting an existing document should create a new canvas with provenance; preserve the original and report unsupported content instead of implying a lossless round trip.

06 / Claude

Make high-quality generation a checked process with bounded revisions.

Generate a plan before a composition

Infer audience, purpose, approximate length, sources, and visual direction. Ask a question only when an answer changes the outcome materially; otherwise choose a reversible default. Build the semantic outline, compose the content, assign recipes, then validate and render. Keep factual content separate from visual judgments.

A small, powerful tool surface

Proposed tools: read_canvas, create_canvas, apply_canvas_patch, set_canvas_theme, render_canvas, inspect_canvas, and prepare_canvas_print. Patch operations target IDs and accept expected revisions. Support idempotency keys so retries do not duplicate sections. A single patch can contain several validated operations applied together.

Validation before publication

Reject invalid nesting, missing assets, unsupported styles, inaccessible labels, and changes to locked content. Check overflow, reading order, small text, excessive density, image readiness, and print renditions. Do not stream partial JSON into the active document. Show valid section-level previews while composing a candidate revision.

Give Claude eyes and measurements

Render at desktop and narrow widths, and inspect the print presentation. Return structured issues with block IDs plus targeted screenshots. Let Claude repair the draft in a bounded loop. Mechanical checks catch clipping; visual review checks composition. On failure, retain the last valid version and explain the unresolved issue.

Security by construction

Normal canvases use validated data and trusted components: no generated scripts, arbitrary HTML, remote imports, or uncontrolled CSS. Validate URLs, sanitize imported SVG, scope asset access, and reject layout values outside supported bounds. Source documents are evidence, never instructions with tool authority. Future executable components require a separate-origin sandbox, restricted network, resource limits, and explicit message validation.

Keep turns efficient

Send an outline, IDs, relevant subtrees, and recent edits before sending whole artifacts. Cache renders by revision and assets. Prefer focused patches and section previews. Only commit a redesign once its complete candidate is valid, so the user's caret and unsaved work are not repeatedly disturbed.

07 / PDF

Pageless while creating. Deliberate pagination when handing off.

One source, two presentations

Both Flow and Pages are fully editable over one content model. Pages is the reference composition for export; Flow may reflow to a different width without changing its content. The PDF pipeline consumes the settled page layout instead of independently laying out the flowing version. Export settings and a controlled browser profile remain important for fidelity.

Browser printing is the first export path

Browser Print / Save PDF should print the already paginated composition, removing editor controls and page gaps while preserving page geometry. The app action prepares a revision-pinned snapshot, waits for assets and layout settlement, then opens the print dialog. Match paper size, remove extra margins, and suppress browser headers to avoid a second, conflicting pagination pass. A controlled Chromium export can later make this more repeatable.

Fragmentation rules per component

Keep short figure/caption units and compact cards together with break-inside where appropriate; allow long prose and long containers to split. Keep headings with the next content where supported. Reflow complex grids to print-safe structures, repeat table headers where supported, wrap long tokens, and define a fallback for wide tables. A container taller than a page cannot remain indivisible.

A static contract for interactive content

Charts have a printable SVG, labels, units, and a data summary. Filters print their current values and as-of time. Tabs expand into ordered sections, or use an explicitly chosen active-only policy. Accordions follow a declared all-content or current-view policy. A simulation prints its inputs and result. Resolve all print representations before opening the dialog.

Know the browser limits

Print CSS can request dimensions, margins, and color preservation, but users and browser engines control final output. Backgrounds, browser headers, page numbering, and fragmentation vary. Exact color preservation is not guaranteed. Cross-browser tests support a readable-output promise; an optional pinned Chromium exporter could later offer a more repeatable output profile.

A practical quality gate

Await document fonts and image decode; fail visibly on required missing assets. Test Letter and A4, narrow and wide tables, long URLs, tall sections, non-Latin text, and grayscale output. Generate PDFs in automation, extract text to detect missing content, and inspect rasterized pages for clipping and bad breaks. Browser print does not itself guarantee a properly tagged accessible PDF.

08 / Delivery

Prove the edit → redesign → print loop before expanding the vocabulary.

First milestone: resolve the hard interaction

Prototype both editable views with a paragraph spanning pages, a two-column comparison, a long table, an image/caption, and a colored section. Exercise cross-page selection, boundary deletion, paste, IME input, undo, resizing, delayed fonts/images, and concurrent Claude edits. Verify that each page picture captures the real DOM and that export preserves the page composition.

Second milestone: ship one complete workflow

Launch proposals and briefs with strong recipes, several visual directions, inline text editing, section rearrangement, focused Claude patches, locks, history, and native browser print. Include library creation, thumbnails, autosave, reopen, and recoverability so canvases feel like durable documents.

Third milestone: widen expression

Add editable chart data, diagrams, brand kits, reusable templates, source-linked claims, and document-to-canvas conversion with clear fidelity limits. Add comparison views for redesign candidates. Introduce custom isolated components only after their editable-slot and print contracts are proven.

Launch acceptance criteria

A user can create a proposal, correct a price manually, ask Claude to redesign it, and reopen it with the correction intact. Stale overlapping patches cannot erase the correction. Failed generation leaves the previous version usable. All intended text appears in Letter and A4 PDFs, with no clipped content in the supported browser matrix.

What to measure

Track time to first useful artifact, accepted generation rate, manual editing success, redesigns that preserve edits, conflict rate, recoverability, print preflight failures, and repeat artifact use. Evaluate design with representative user tasks and human review; model confidence and screenshot similarity are insufficient quality measures.

Scope and uncertainty

This is a product and architecture proposal grounded in the current repository, not an implemented feature or a delivery estimate. Editor-container behavior and browser fragmentation need a technical spike. Estimate implementation only after those risks are measured and the first component set is fixed.
